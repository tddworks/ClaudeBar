# ClaudeBar PR 赞助回馈计划

## 1. 计划概述

为了感谢开源社区对 ClaudeBar 的贡献，项目设立 PR 贡献回馈计划。金额不大，但规则透明、机会公平、预算可控。

### 核心规则

- 每个符合条件并成功合并的 PR，奖励 1 美元。
- 每个 UTC 自然日最多奖励 1 个 PR。
- 每个自然月最多奖励 30 个 PR。
- 同一天内，最先合并的有效 PR 获得当天奖励。
- 当月名额用完后，后续 PR 不再计入当月奖励。
- 提交 PR 前，必须先提交问题说明或功能提案，并获得项目维护者采纳。
- 只有针对已采纳 Issue 的有效 PR，才有资格进入奖励审核。
- 最终资格由项目维护者根据 Issue、PR 的实际价值和质量确认。

## 2. 计划目标

1. 感谢帮助改进 ClaudeBar 的贡献者。
2. 鼓励 Bug 修复、功能、测试和文档贡献。
3. 让奖励规则简单易懂，避免复杂申请流程。
4. 通过每日和每月上限控制预算。
5. 公开记录奖励结果，保证过程可追溯。

## 3. 预算与时间标准

- 单个奖励：1 美元。
- 每日最高支出：1 美元。
- 每月最高支出：30 美元。
- 实际支出可能低于上限，取决于当月有效 PR 数量。

所有时间统一使用 UTC。PR 的创建、审核或批准时间不影响排序，只有实际合并时间用于判断先后。

## 4. Issue 优先：PR 的前置条件

为了避免机器人提交、重复提交和低价值 PR，贡献者必须先提交 Issue，清楚说明问题、使用场景或功能需求。

Issue 必须经过项目维护者确认采纳后，贡献者才应开始提交 PR。建议使用以下 Label：

- `accepted`：问题或提案已被项目采纳。
- `sponsor-reward-eligible`：该 Issue 可以通过 PR 参与赞助奖励。
- `in-progress`：已有贡献者开始处理。
- `wont-fix`：项目决定不处理。

Issue 被采纳只代表项目认可这个方向，不代表一定获得奖励，也不代表一定会合并 PR。每日奖励、每月 30 个名额、PR 质量和维护者最终审核仍然有效。

PR 必须明确关联已采纳的 Issue，例如在 PR 描述中使用 `Fixes #123` 或 `Closes #123`。一个 PR 原则上只对应一个奖励 Issue；如果多个贡献者处理同一个 Issue，维护者应提前确认协作方式，避免重复实现。

## 5. 有效 PR 条件

一个 PR 通常需要满足以下全部条件：

1. 在提交 PR 前，已经提交对应 Issue，并获得项目维护者采纳。
2. PR 描述明确关联已采纳的 Issue。
3. 提交到项目默认分支或指定目标分支。
4. 由项目维护者正式合并。
5. 为已采纳的 Issue 提供实际且有意义的解决方案。
6. 通过必要的 CI 检查。
7. 遵守项目代码规范和贡献指南。
8. 不是项目维护者本人提交的 PR。
9. 不是重复或高度相似的 PR。
10. 合并后没有在短期内被回滚。

可参与奖励的类型包括 Bug 修复、新功能、测试、文档、CI/CD、性能、无障碍、安全和代码质量改进。

## 5. 不符合奖励条件

- 未经 Issue 采纳就直接提交的 PR。
- 与已采纳 Issue 无关或超出 Issue 范围的 PR。
- 自动生成的依赖更新 PR。
- 没有实际价值的纯格式化修改。
- 重复提交或高度相似的 PR。
- 为增加奖励次数而拆分的低价值 PR。
- 垃圾、恶意、明显低质量或仅用于刷奖励的提交。
- 维护者本人提交的 PR。
- 合并后很快被回滚或未通过 CI 的 PR。
- 当天已有更早合并的有效 PR。
- 当月 30 个奖励名额已经用完的 PR。

项目维护者可以拒绝利用规则、影响项目质量或增加不必要维护成本的提交。

## 6. 奖励确认流程

1. 贡献者先提交 Issue，说明问题、需求、场景或改进目标。
2. 维护者确认 Issue 是否采纳，并添加 `accepted` 和 `sponsor-reward-eligible`。
3. 贡献者提交 PR，并在描述中关联该 Issue。
4. PR 被合并。
5. 维护者确认 PR 是否符合 Issue 范围并具备实际价值。
3. 检查该 UTC 日期是否已有奖励 PR。
4. 检查当月是否达到 30 个奖励名额。
5. 符合条件时添加 `sponsor-reward` 和 `sponsor-reward-pending` Label。
6. 在奖励记录中登记 PR 编号、贡献者和合并日期。
7. 月底统一确认收款方式并发放奖励。
8. 发放完成后更新为 `sponsor-reward-paid`。

不符合条件的 PR 可以添加 `sponsor-reward-ineligible`，并在必要时说明原因。

## 7. GitHub Label 设计

- `sponsor-reward`：确认符合基本奖励条件。
- `sponsor-reward-pending`：已入选但尚未发放。
- `sponsor-reward-paid`：奖励已经发放。
- `sponsor-reward-ineligible`：不符合奖励条件。
- `sponsor-reward-daily-limit`：当天名额已被占用。
- `sponsor-reward-monthly-limit`：当月名额已用完。

## 8. 奖励记录

建议在 `docs/sponsor-rewards.md` 或 GitHub Discussion 中维护公开记录：

| UTC 日期 | PR | GitHub 用户名 | 状态 |
|---|---|---|---|
| 2026-08-17 | #123 | @contributor | Pending |

公开记录只保留 UTC 日期、PR 编号和链接、GitHub 用户名及奖励状态。不要公开邮箱、真实姓名、收款账号或其他敏感信息。

## 9. 奖励发放方式

建议每月底统一审核和发放，而不是每个 PR 合并后立即处理，以减少人工操作和误发风险。

- 首选 GitHub Sponsors。
- 也可以使用双方认可的其他合法付款方式。
- 无法收款的贡献者可以将奖励捐回项目、捐给公益组织或放弃奖励。

贡献者无需在公开 PR 或 Issue 中发布付款信息，应通过安全的私下方式确认。项目不承诺超出实际支付能力的付款方式或金额。

## 10. 自动化方案

第一阶段不直接自动付款。GitHub Action 可以自动检查和记录，维护者保留最终确认权。

PR 合并时的判断逻辑：

1. 判断提交者是否为维护者。
2. 判断 CI 是否通过。
3. 排除自动依赖更新和明显低价值改动。
4. 获取 UTC 合并日期。
5. 查询当天是否已有奖励 PR。
6. 查询当月已确认的奖励数量。
7. 名额已满时添加对应状态 Label。
8. 否则添加 `sponsor-reward-pending` 并更新记录。
9. 发布状态评论。

建议文件结构：

```text
.github/
  CONTRIBUTING.md
  workflows/
    sponsor-reward.yml
docs/
  sponsor-rewards.md
  sponsor-rewards.zh-CN.md
```

## 13. 分阶段落地计划

### 第一阶段：公开规则

- 发布中文和英文文档。
- 在 `CONTRIBUTING.md` 中增加入口链接。
- 创建并统一使用相关 Label。
- 通过 GitHub Discussion 收集反馈。

### 第二阶段：人工运行

- 维护者手动确认有效 PR。
- 每天检查第一个有效合并 PR。
- 每月维护奖励清单。
- 月底统一发放奖励。

### 第三阶段：半自动化

- 使用 GitHub Action 监听 PR 合并事件。
- 自动检查每日和每月名额。
- 自动添加 Label 和发布状态评论。
- 维护者保留最终确认权。

### 第四阶段：复盘优化

运行 1～2 个月后，评估参与者数量、有效 PR 比例、维护者审核时间、发放成功率、争议情况和预算使用情况，再决定是否调整规则。

## 14. 风险与处理原则

- 低质量 PR 增加：以实际价值、CI、重复提交和维护成本进行筛选。
- 同日争议：统一使用 GitHub 实际合并时间和 UTC 日期，并保存 PR 链接。
- 无法收款：允许捐回项目、捐赠公益组织或放弃奖励。
- 工作量增加：先人工运行，再逐步自动化，不直接自动付款。
- 预算超支：严格执行每日 1 个和每月 30 个上限。

## 15. 重要说明

本计划是对开源贡献的自愿感谢，不构成雇佣关系、合同或付款保证。项目可以随时修改、暂停或终止本计划，相关变更会记录在本文档中。

最终奖励资格、奖励时间和发放方式均以项目维护者的确认结果为准。

感谢每一位帮助 ClaudeBar 变得更好的贡献者！
